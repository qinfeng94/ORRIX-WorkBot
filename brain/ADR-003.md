# ADR-003 · 大额审批流采用 Inngest + 代码算术校验的「双引擎同构」状态机

> 状态：已采纳（Day 18 上线）· 出处：`docs/architecture/WORKBOT-PRODUCTION-ARCHITECTURE.md` §ADR-003
> 证据：`src/lib/workflow/engine.ts` + `src/lib/workflow/inngest.ts` + `app/api/workflows/*` + `app/api/inngest/route.ts`

## 背景

FIN-001 审批窗口最长 7 天，绝不能依赖进程内存挂起；算术校验若交给 LLM 可能被诱导「凑平」（违反验收考卷 Q6）。

## 决策（四条支柱）

1. **双引擎同构**：状态机函数与编排引擎解耦——postgres（默认等价演练，API 直接调状态机）与 inngest（真实 Dev Server，`npx inngest-cli@latest dev`）调用**同一批函数**；引擎选择失败自动降级 postgres 并在响应 notice 说明。
2. **挂起不占内存**：等待审批的挂起态只存 `workflow_runs` 行（`suspended_at` / `wait_expires_at`），零定时器零进程内状态；跨重启证明 = `PROCESS_START_MS > suspended_at + 1s`，确定性判定。
3. **算术纯代码**：Σ 数量×单价 vs 申报总额，不过即 `phase=invalid` 步骤 1 红灯拦截，**不进入挂起**；结论 100% 可复现。
4. **批准幂等 + 零打款**：`completeRun` 事务内 `FOR UPDATE` 检查 phase，已完成返回原凭据、路由回 409，绝不产生第二张凭据；批准后只写 `approval_audit_logs` 凭据 + 通知下游事件，全程零打款动作。AI/匿名/值班审批人 403（复用 `isValidNamedApprover`）。

## 配套不变量

- `workflow_events` 事件流水只增不改（触发器物理拒绝 UPDATE/DELETE）；`workflow_runs` / `mcp_tasks` 是状态表，`engine.ts` 是唯一 UPDATE 入口。
- FIN-001 徽章沿用 `isLargeAmount`（财务部且 >¥50,000，「等于」不触发）。
- MCP Tasks 进度是时间的确定性函数：`progress = (now - started_at) / total_ms`，结果开工前定稿落库，100% 才揭晓；创建返回 HTTP 202 + taskId + 轮询 statusUrl。
- 跨组织 A2A 验真（外部华东物流代理）：客户端 2500ms 超时熔断 + 连续失败 2 次开熔断器冷却 30s；假单/查无此单/超时/熔断一律转人工，绝不硬凑「验真通过」。
- inngest SDK v4.27 API 差异：`createFunction` 两参数（trigger 并入 `options.triggers`）；`waitForEvent` 泛型是事件选项类型，返回值用 `unknown` + 类型守卫收窄；客户端 `isDev: true` + baseUrl `127.0.0.1:8288`；`send` 返回 `{ ids }`。

## 后果

- 审批流断电不丢、可证明恢复；代价是多一张状态表 + 事件流水表的写入约定。
