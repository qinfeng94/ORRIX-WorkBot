## 二、地雷发现过程复盘

### 2.1 发现方法论：「活体取证 → 逆向读码 → 行号钉死 → 测试证实」四步法

这 5 颗地雷**不是靠肉眼看代码猜出来的，而是靠证据链钉死的**。顺序很关键：

```mermaid
flowchart LR
    A[第1步 活体取证<br/>先跑一遍脏数据] --> B[第2步 逆向读码<br/>剥皮还原业务流程]
    B --> C[第3步 行号钉死<br/>每颗雷定位到具体行]
    C --> D[第4步 测试证实<br/>写成必然失败的回归测试]
```

**第 1 步：活体取证（先跑，再读）。**
拿到烂代码第一件事不是通读 813 行，而是直接喂脏数据跑一次。这一跑抓到了 5 类「现场证据」：
- TCK-5004 扣款指令发出 **3 次**（重复扣款现行犯）
- TCK-5007 **死循环卡死整批**（最后靠人工切断，Kill Switch 演练顺带完成）
- TCK-5002 结算 492,938 分（比正确值少 1 分）
- TCK-5005 一行 `Cannot read properties of null` 后被静默跳过
- 每行日志都印着 18 位明文身份证号

活体取证的价值：**先知道"病发作的样子"，再去代码里找"病灶"**，方向感完全不同。

**第 2 步：逆向读码（剥皮还原流程）。**
把 813 行代码剥成一句话：「读工单 → 洗数据 → 校验 → 换汇 → 标审批 → 扣款 → 记台账」。画出业务流程图后，每个异常证据都能挂到具体环节上——比如「扣款指令发 3 次」直接指向扣款循环。

**第 3 步：行号钉死。**
用关键词检索把每颗雷定到具体行（重构前行号）：

| 雷号 | 位置 | 病灶一句话 |
|---|---|---|
| #1 旧阈值 | L26 | `100000` 硬编码，2025 已废止的 10 万制度 |
| #2 重复扣款死循环 | L347 | `while(PENDING)` 无幂等键重扣 |
| #3 浮点丢分 | L91 | `parseInt` 截断代替四舍五入 |
| #4 空税号崩溃 | L258 | `null.startsWith()` 裸调 |
| #5 PII 明文 | L441 | 日志直接拼证件号 |

**第 4 步：测试证实。**
每颗雷写成一条「必然失败」的回归测试。这一步是发现过程的收官——**测试红 = 地雷实锤**，没有任何「我觉得可能有风险」的主观判断。

### 2.2 发现过程中的关键洞察

1. **注释是最好的口供，也是最坏的陷阱。** 遗留代码里的「老周批注：从来没出过事」「老板说的勿动」全部不可信——脚本自带的「事故回忆录」（附录 A）反而和 5 颗雷一一对应。棕地接管时，**事故史比维护者声明更可信**。
2. **脏数据集是探雷器。** 14 张工单不是随便造的：每颗雷都有一条专门设计来踩响它的数据（HOLD/STUCK 银行状态、null 税号、带小数的外币金额、5 万边界 ±1 元）。没有脏数据，烂代码跑起来「看起来正常」。
3. **一次跑批同时暴露多颗雷。** 全量试跑让 5 颗雷在一次输出里集体现形，取证成本极低。前提是:数据集要脏得有针对性。

## 三、修复策略复盘

### 3.1 总策略：先红后绿，一次性安全重构

```
写 5 条必然失败的回归测试（红）
        ↓ 留证：tests 8 / pass 3 / fail 5
一次性重构，逐颗拆雷
        ↓
跑同一套测试（绿）：tests 8 / pass 8 / fail 0
        ↓
端到端重放同一批 14 张脏工单，逐单前后对照
```

三条铁律：

1. **测试先行，红必须留证。** 先写测试并跑出 5 红 3 绿的成绩单，再动代码。没有「红」的留证，后面的「绿」无法证明拆雷真的发生过。
2. **基线用例护住「零回归」。** 3 条基线用例（整数换分精确、无尾差换汇、正常工单不触发审批）在重构前后**都必须绿**——它们守住的是「修好了坏行为，没弄坏好行为」。这是棕地重构和推倒重写的本质区别。
3. **一次跑批验证，逐单对照。** 同一批脏工单重构前后各跑一遍，输出逐工单对照表（侦察报告第五节），任何行为变化都能被解释：要么是修复预期内，要么是回归。

### 3.2 每颗雷的修复要点

| 雷号 | 修复策略 | 设计取舍 |
|---|---|---|
| #1 旧阈值 | `FIN001_APPROVAL_THRESHOLD = 50000`，注释钉死现行 FIN-001 | 两个细节：①「超过」才触发，等于 50,000 不触发（TCK-5008 用例钉死边界）；②从「标记后照扣」改为**停止扣款、出审批单转具名审批人**——审批必须有牙齿 |
| #2 重复扣款 | 单次指令 + 幂等键（`工单号:结算日`）+ PENDING 只轮询 `query` + 轮询上限 5 次转人工 | 关键取舍：**绝不重扣**。银行「处理中」≠ 扣款失败，重发指令才制造重复扣款；STUCK 场景宁可转人工也不死循环 |
| #3 浮点丢分 | 全链路 `Math.round(x * 100)` 统一四舍五入 | 修复前先用 node 实测各候选数字的浮点行为，避开 `.5` 边界陷阱（如 `108736.4999` 会双向翻车），保证「遗留必败、修复必过」 |
| #4 空税号 | 空值防御前置：null/空串/非字符串一律转人工补录清单 | 取舍：不猜、不兜底默认值、**绝不扣款**。宁可单据挂起等人补，不可静默吞钱 |
| #5 PII 明文 | `maskIdNumber`（前6后4）/ `maskTaxId`（前4后4），所有日志出口统一过脱敏 | 防御放在**出口处**（logAudit 层），而不是要求每个调用点自觉——一处收口，全站生效 |

### 3.3 修复中的意外收获

重构时发现仿真银行桩的 `query` 接口「当年没开发完」（永远返回 UNKNOWN）——这正是棕地的典型形态：**你修 A 的时候，必然踩到 B 的坑**。处理方式：补全查询接口并与测试桩行为对齐，作为 v4 重构的一部分记录在案。教训：重构预算要留 20% 余量给「顺藤摸瓜」。

## 四、最佳实践沉淀（可复用清单）

### 4.1 棕地接管七步清单（下次直接照做）

1. **先跑再说**：用针对性脏数据跑一遍，抓活体证据（崩溃点/卡死点/异常输出）；
2. **逆向画流程**：把代码剥成一句话业务流程图，人话讲给业务方听；
3. **事故史优先**：翻事故记录/投诉记录，比维护者注释可信；
4. **行号钉雷**：每颗雷定位到行，写进侦察报告，任何人可复核；
5. **测试钉雷**：每颗雷一条必然失败的回归测试，跑红留证；
6. **基线护体**：重构前先固化「必须保持不变」的行为为基线用例；
7. **重构 → 全绿 → 端到端重放**：一次跑批逐单对照，零回归才算收工。

### 4.2 金融类遗留代码的五条审计直觉

- **看到硬编码金额阈值 → 立刻查现行制度**（本例：10 万旧制度已废止，漏审 5~10 万区间）；
- **看到 while 重试写操作 → 立刻查幂等键**（没有幂等键的重试 = 重复扣款制造机）；
- **看到金额 × 浮点 + parseInt/floor → 立刻怀疑丢分**，用真实数字实测而不是推理；
- **看到 `字段.方法()` 无空值防御 + 外部数据源 → 必然有崩溃雷**；
- **看到日志拼用户字段 → 立刻查脱敏**，PII 泄漏常是「为了排查方便」的好心办坏事。

### 4.3 流程纪律（本项目红线在演练中的落点）

- **Kill Switch 实操**：死循环进程在秒级内人工切断，日志全程留痕——「物理切断优先」不是纸面制度；
- **审批门禁有牙齿**：超阈值不只是「标记」，而是停止扣款 + 生成审批单号 + 挂起转人工，AI 只起草、放行归人；
- **数据虚构 + 本地仿真**：全部证件号/税号/金额为虚构演示数据，网关为本地仿真桩，零正式系统接触。
